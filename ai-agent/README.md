# Fineract Query Agent

A natural-language query agent over [Apache Fineract](https://github.com/apache/fineract)'s
core banking schema. Ask about clients, loans, arrears and savings; every figure
in an answer is retrieved by SQL, never generated by the model.

Built inside a fork of Fineract so the schema is the real one — 281 tables from
an actual Liquibase run, pruned to the 32 the agent needs — rather than a
simplified model invented to make the demo easy.

## The one decision that matters

**The model cannot write SQL.** It chooses among six fixed tools and supplies
arguments, which are bound as parameters. Prompt injection can reach a
legitimate query with odd arguments; it can never reach arbitrary SQL.

That is a security property, but the stronger reason is correctness. Fineract's
domain is full of traps that produce *plausible wrong numbers* rather than
errors:

| Trap | What the naive query does |
|---|---|
| `is_reversed` is a flag, not a delete | counts money that never moved |
| `ACCRUAL` (type 10) sits beside real repayments | counts accounting entries as cash |
| Cleared instalments drag `MIN(duedate)` back | ages every loan to its origination |
| Per-loan `grace_on_arrears_ageing` | reports loans that are not actually late |
| Loans ⋈ savings fan-out | double-counts savings balances |
| `m_loan.client_id` is nullable (group loans) | silently drops loans from a client join |

Every one of these is enforced in Java, not in the prompt. **An instruction the
model can silently forget is not a control.**

And the fact that shapes everything: **Fineract has no OVERDUE loan status.** A
loan 200 days late is `ACTIVE`, exactly like a current one. Arrears is computed
from the repayment schedule using Fineract's own definition — business date
minus the oldest unpaid due date, honouring each loan's grace period — and is
never stored. Ask the agent for "status OVERDUE" and it refuses and tells you
why, rather than returning an empty list that reads as "nobody is behind".

## Running it

Requires a Postgres database and a Gemini API key
([AI Studio](https://aistudio.google.com/api-keys), free tier).

```bash
export AGENT_DB_JDBC_URL='jdbc:postgresql://<host>/fineract_agent?sslmode=require'
export AGENT_DB_USER=... AGENT_DB_PASSWORD=... GEMINI_API_KEY=...
cd ai-agent && mvn spring-boot:run
```

Flyway applies the schema, reference tables and seed on first start against an
empty database. Then open <http://localhost:8080>.

| Endpoint | Purpose |
|---|---|
| `GET /` | the demo page |
| `POST /api/ask` | `{"question": "..."}` → answer plus latency, tokens, tool calls |
| `GET /api/stats` | pass-through cost and latency stats, circuit state, token budget |
| `GET /api/health/db` | row counts, to separate "wrong answer" from "wrong database" |

## Migrations

| File | Contents |
|---|---|
| `V1__fineract_schema.sql` | 32 tables generated from a real Liquibase run, names verbatim |
| `V2__reference_tables.sql` | 7 `r_*` tables derived from Fineract's Java enums |
| `V3__seed_foundation.sql` | offices, staff, products, delinquency ranges |
| `V4__seed_portfolio.sql` | 200 clients, 350 loans, schedules, transactions, savings |

`V1` was **generated, not written**: `0001_initial_schema.xml` is a frozen
Flyway→Liquibase baseline with ~290 migrations layered on top, and `m_loan`
alone is altered by 34 of them. `scripts/stage1/dump-fineract-schema.sh` runs
Fineract's own changelogs against a throwaway database and
`scripts/stage1/prune-schema.sh` reduces the dump to the FK-closed subset —
recomputing the table set each run, so it cannot drift from upstream.

The seed's rollups are **computed from the transactions it writes**. Fineract's
~40 `_derived` columns are maintained by its Java write path, which we are not
running, so nothing would ever repair an inconsistency. 17 invariants in
`scripts/stage1/verify-seed.sql` assert the seed reconciles — without that, the
eval suite would prove nothing, because expected answers computed in SQL would
agree with a broken agent.

## Evals

The suite is 33 tests overall; 32 need neither a database nor an API key and
run on every CI build. The 30 eval questions need both.

30 questions whose expected answers are computed in **plain SQL, written
independently of the tools**. Reusing the implementation's own query would prove
only that it is deterministic.

```bash
cd ai-agent && mvn -Dtest=EvalSuiteTest test
```

Failures are categorised — `WRONG_VALUE`, `NO_VALUE`, `ANSWERED_UNANSWERABLE`,
`REFUSED_ANSWERABLE`, `ERROR` — because a pass rate says how much is broken and
the breakdown says what to fix. Four cases are guardrails where a confident
answer *is* the failure: a status that does not exist, an office that does not
exist, a prediction, and an out-of-scope question.

The suite asserts a pass-rate floor rather than perfection. Temperature is 0.0,
which makes the model near-deterministic but not guaranteed so, and a suite that
red-builds on one flaky phrasing stops being run.

## Reliability

| Control | Why |
|---|---|
| Request deadline (90s) | a slow model otherwise holds a thread open; on Cloud Run you pay for it to wait |
| Circuit breaker (4 failures) | when the provider is down, queueing more calls turns an outage into thread exhaustion |
| Daily token cap | free-tier key on a public URL: one visitor should not exhaust the quota for everyone |
| Rate limit (6/min) | applied only to endpoints that cost money |
| Read-only DB role | rollups are maintained by code we do not run, so any write corrupts permanently and undetectably |
| `ToolResult` never throws | a thrown tool error is fed back as raw text and parsed as JSON, so a SQL error becomes a Jackson crash |

Failures are distinguished for the caller: a refusal is `503` with a readable
reason, not a bare `500`. "Not now" and "broken" are different, and a user can
act on the difference.

## Trade-offs

**Spring Boot 4.1 rather than 3.x.** The Gemini free tier needs API-key auth,
which exists only in Spring AI 2.0's `google-genai` starter, and Spring AI 2.0
requires Boot 4. Spring AI 1.0's only Gemini option is the Vertex AI starter,
which needs a GCP project and service-account credentials — billed, not free.

**JDBC, not JPA.** Every query is a read-only reporting query whose SQL must
match Fineract's own semantics for arrears and rollups. An ORM would add a
mapping layer whose only job is to get out of the way.

**Individual loans only.** `m_loan.client_id` is nullable because group loans
hang off `group_id`, so a client join silently drops them. Restricting scope is
fine; inheriting the restriction by accident is not, so the tools state
`client_id IS NOT NULL` explicitly rather than implying it through a join.

**Pinned business date (2026-06-30).** Fineract uses a configurable logical
business date, not `CURRENT_DATE`. Pinning it means "over 60 days in arrears"
has one correct answer forever, so an eval failure is a regression rather than
the calendar moving.

**In-memory stats and rate limiting.** Honest for a single container. Behind
several instances the rate limit becomes per-instance and the daily token cap is
the backstop that actually bounds spend.

## Deploying to Cloud Run

```bash
gcloud run deploy fineract-query-agent \
  --source ai-agent --region <region> --allow-unauthenticated \
  --set-env-vars AGENT_DB_JDBC_URL=...,AGENT_DB_USER=agent_ro \
  --set-secrets AGENT_DB_PASSWORD=agent-db-password:latest,GEMINI_API_KEY=gemini-key:latest
```

Create the read-only role first with `scripts/stage6/create-readonly-user.sql`.
Flyway must keep running as the **owner** — migrations create tables and
`agent_ro` cannot. Deploy-time writes are authorised; request-time writes are
not.
